# MyDesk LAN

独立的 Windows x64 局域网远程桌面：UDP 视频，TCP/TLS 键鼠和剪贴板，UDP 不通时自动降级 TCP 视频。源码、配置、端口与原云端版本分离；不需要运行 server.go。

## 直接运行

请使用 `dist` 中的 **4.20-key-match** 主控与被控，LAN 协议仍为 v6。本次只改连接入口：先输入密钥，自动匹配局域网设备；唯一空闲匹配直接连接，多台匹配由你选择，同一设备多个 IP 合并。自动匹配需要更新两端，指定 IP 仍可连接旧 v6 两端。视频、画质、FPS、鼠标、剪贴板、最小化和 F7/F8 文件传输不改，不新增文件剪贴板。FFmpeg 和原有画面参数不用更换。保留 4.19 剪贴板安全修复、4.18 发送优化、纯内存路径记忆、分辨率自动同步及 GPU 显示。云端版本的画面与控制逻辑未改；为避免公开部署地址，云端客户端和主控端默认连接本机 `127.0.0.1:19998`，可通过 `MYDESK_SERVER_URL` 或 `-server` 指定服务端。

最少复制：被控端只需 `lan_client.exe`，主控端只需 `lan_controller.exe`，即可使用区域 JPEG；不需要服务端。H.264 路线的被控端仍需要 `ffmpeg.exe`，旧 NVIDIA 驱动建议再带 `ffmpeg-compat.exe`。4.10 主控在 Windows 原生解码器可用时，不带 FFmpeg 也能接收 H.264；建议首次对照测试先保留旁边的 `ffmpeg.exe`，用于原生路线不兼容/持续积压时自动回退。文件放在各自 EXE 旁边。启动 CMD、配置防火墙 CMD 和说明文档都是可选的。

被控机器：

```powershell
.\lan_client.exe
```

窗口显示 IP 和随机配对码。主控机器：

```powershell
.\lan_controller.exe
```

先输入被控端的配对码作为连接密钥，再自动发现并匹配。只有一台空闲匹配就直接连接；多台同密钥设备列出名称、IP 和空闲/占用状态，由你选择序号。也可只提供密钥、不填 IP：

```powershell
.\lan_controller.exe -code <被控端显示的配对码>
```

也可以明确指定 IP，这时只连接指定目标，失败不改连其他设备：

```powershell
.\lan_controller.exe -connect 192.168.1.20 -code <被控端显示的配对码>
```

发现/控制默认端口为 TCP+UDP 29860；视频另用会话分配的 UDP 端口。连接始终先走 TCP/TLS 配对，随后才探测 UDP 视频；UDP 不通自动退回 TCP，TCP 本身不通时不能靠切换视频传输协议解决。

## 密钥自动匹配（4.20）

密钥沿用现有配对码，不另建账户或服务器。被控端未指定 `-code` 时仍每次启动随机生成；希望固定可用 `.\lan_client.exe -code <固定密钥>`，至少六个字符，注意大小写。主控可交互输入或用 `-code` 指定，不新增密钥配置文件。

- 只有一台匹配且空闲：直接连接，显示实际设备名和 IP，不要求再填地址。
- 多台匹配：全部列出供选择，包含占用状态；即使只剩一台空闲，也不替你选。占用设备不可按序号连接，不抢占其原会话。
- 同一被控进程的多个地址经验证后合并为一项，保留可用地址供正式连接尝试。同名但不同进程/电脑不按名称合并。显示设备名会去掉终端控制字符。
- 没有匹配、唯一设备占用或选择列表中：可输入 `r`（或空回车）重新搜索、`k` 更换密钥、`q` 退出，也可输入明确的 IP[:端口]。无有效输入/输入结束不会默认选择第一台。
- `-connect IP[:端口]` 优先，完全跳过发现/自动匹配；指定地址无法连接或密钥错误，不会悄悄连接另一台同密钥设备。`-list` 仍只列出发现结果，不要求密钥、不创建会话。

发现广播只增加能力标记 `key-match-v1` 和随机的进程身份，不广播明文密钥、固定密钥哈希或匹配证明。对发现到的地址做短 TCP/TLS 探测，在现有 TLS 通道导出材料上使用独立的匹配角色证明，双方都验证；不把普通配对证明用于匹配，也不创建视频会话、探测采集/编码器、修改输入/剪贴板或挤掉已有主控。身份、名称和占用状态以 TLS 验证结果为准，不凭广播里声称的 ID/名称合并设备。正式连接仍重新配对、重新检查占用，因此列表状态不构成会话预留。

匹配最多四路并发、每轮最多 128 个去重地址；单地址申请两秒期限，整轮申请六秒预算。只检查已发现的地址，不扫描整个网段；不响应/密钥不同的地址不进入选择列表，超出数量上限会提示。Windows/Go 调度不是硬实时期限保证。仅发现到旧 v6 被控时会提示更新或指定 IP，不用正式配对去试探旧设备，避免发现过程触发编码或占用。旧设备的显式 IP 连接继续兼容。

自动匹配不是穿透：广播被防火墙、VPN 或 AP 隔离时，单凭密钥无法知道设备 IP，仍可指定地址连接。不会新增服务器、修改防火墙/VPN 设置或自动保存密钥。

## 防火墙、VPN 和网卡选择

普通启动不会修改系统配置。需要时双击被控端的 `configure_client_firewall.cmd`、主控端的 `configure_controller_firewall.cmd`，或分别执行：

```powershell
.\lan_client.exe -firewall setup
.\lan_controller.exe -firewall setup
```

操作请求 UAC 管理员权限，并显示确认框；只添加当前 EXE 的 TCP/UDP 入站规则，来源限制为本地子网，覆盖专用、公用和域配置文件。不会关闭防火墙、不改出站策略、不改 VPN。可以用同一程序的 `-firewall remove` 撤销。规则绑定程序路径，移动 EXE 后需重新配置；删除旧路径规则要在旧路径执行撤销。若管理员策略禁止本地规则或存在更高优先级阻止规则，仍需管理员处理。

默认通过各网卡绑定的 UDP socket 进行发现，物理以太网/Wi-Fi 优先，VPN/虚拟网卡随后；同一设备多个地址会合并选择，连接时尝试多个地址/匹配子网的本地 IP。物理网卡识别优先使用 Windows `Get-NetAdapter -Physical`，不可用时回退名称启发式。TCP 控制、视频连接及 UDP 会话使用同一本地 IP。

```powershell
# 查看可选本机网卡
.\lan_controller.exe -list-interfaces
.\lan_client.exe -list-interfaces

# 可填写网卡名称或本机 IPv4；被控端指定后仅在该地址监听
.\lan_client.exe -interface "以太网"
.\lan_controller.exe -interface "以太网" -connect 192.168.1.6

# 强制 TCP 视频，编码器保持不变
.\lan_controller.exe -connect 192.168.1.6 -transport tcp
```

广播被隔离时可以直接 `-connect IP`；多台同密钥匹配设备输入列表序号选择，也可输入 IP。日志分别标出发现、TCP/TLS 连接、配对、编码协商、视频连接、UDP 探测和降级原因。4.3 起主控端不再每秒打印标题栏统计，速率/FPS 仍在标题栏实时显示。普通连接失败会弹出诊断框，避免双击 EXE 后控制台关闭看不到错误；无界面测试模式不弹框。连接超时只是现象，不会武断认定一定是防火墙。本包 `-version` 为 `4.20-key-match / protocol v6`；旧 v6 可继续显式指定 IP 互连，自动密钥匹配需新版两端。

## 长文本剪贴板安全与占用诊断（4.19）

上传失败、源校验失败或完成确认不确定时，主控保留第一次尝试的目标剪贴板序号。后续轮询如果发现被控已有新复制内容，就放弃那份旧上传；不会把旧主控文本重新当作新复制去覆盖它。目标未变化的暂时失败仍可重试，目标已成功持有同一内容则不重复写入。新复制的文件/超限内容只留在本机，不做文件跨端粘贴；同为不支持格式但序号不同，也保护其新复制事件。

系统剪贴板打开期间只克隆原始字节，UTF16 转换、PNG 验证、DIB 转 PNG 和摘要计算在关闭之后处理。读取完成后采样序号，允许 Windows 延迟提供/自动合成格式引起的序号变化；释放后又发生新复制则放弃该快照。成功打开后的正常/失败路径都尝试关闭，关闭失败明确报错。文本同时按 UTF16（含结束符）和 UTF8 网络内容检查原有 2 MiB 上限，超限跳过不截断；例如 168499 个常见中文字符在限制以内。后续短文本正常继续同步。

`[lan][clipboard]` 错误现在注明读取主控、读取被控或同步方向。持续占用时额外显示 Windows 错误、打开剪贴板窗口的 PID/TID/HWND，以及内容所有者；不打印剪贴板文本。内容所有者不一定是占用者；其他程序以 NULL 窗口打开时，打开者可能无法识别。仍约五秒限频打印，没有增加视频诊断日志。

这修复了可复现的失败重试覆盖漏洞，不保证能解除其他程序持有的系统锁，也不能直接证明用户现场的持续占用者。F7 关闭同步只取消本程序的同步，不会强行关闭其他程序的剪贴板或结束其进程。若关闭后本机复制仍不能恢复，可先暂时退出并行运行的原版被控/剪贴板工具作对照，再复现时保留新版占用日志；原版即使未连接主控也有剪贴板监测代码，是否为本次原因仍需实际验证。

## 减少突发拥塞与恢复停顿（4.18）

两项被控端优化默认开启，可独立关闭，不增加视频队列容量、不改质量、分辨率、码率公式、编码器参数或 120 FPS 上限，也不重新加入静止降帧。

- `-queue-grace`：健康的两帧队列仍立即入队。只有队列已满才申请一次 4 ms 的短等待；及时腾出位置就保留原编码器和参考顺序，仍满则沿用原有编码重启/新关键帧恢复。超时/取消不任意跳过压缩 P 帧，旧 100 ms 过期帧保护仍保留。4 ms 是本地等待预算，Windows/Go 调度不是硬实时保证。
- `-udp-smoothing`：UDP 每批最多 32 个分片，批间让出 Go 执行机会，不对正常帧额外加固定睡眠，也不把视频按低目标码率慢慢发送。缓冲不足/暂时无法发送时，仅重试失败的那个分片，已成功发送的不会重放；最多安排三次重试，首次资源错误后的恢复窗口为 4 ms。整个视频分片发送仍沿用一次性的 60 ms 绝对期限，批次/补包不会不断延长期限。持续错误、超时、权限/网络/关闭错误仍降级 TCP 并恢复新参考链，不绕过防火墙或 VPN。
- 补包请求移到发送线程，容量限制为八条；在视频批间和 JPEG 无后续新帧的空闲期处理，不让控制线程等待网络写。补包仍最多 256 个索引、100 ms 缓存期限，并限制单次发送工作期限；当前视频优先，补包过期/队列满会等待现有后续 NACK/关键帧恢复机制。探测/后台保活与视频共享短批次写锁，避免修改 socket 期限时干扰正在发送的视频。

```powershell
# 默认使用优化，其他启动参数沿用原配置
.\lan_client.exe

# 在同一新版中关闭两项优化，对照 4.17 的发送/队列策略
.\lan_client.exe -queue-grace=false -udp-smoothing=false

# 只在定位卡顿时启用统计；默认不增加周期诊断日志
.\lan_client.exe -send-stats
.\lan_controller.exe -connect 192.168.1.20 -q 100 -r sharp -latency-stats
```

`-send-stats` 每约 5 秒输出 `[lan][send/local]`：编码输出间隔、满队列等待、已编码帧排队年龄、发送提交时间的 p50/p95/p99，以及队列满/缓解/超时、编码启动尝试、参考恢复、UDP 发送错误/重试/成功恢复/降级、过期帧和补包队列丢弃计数。每项最多 512 个最近样本，输出后清零；编码输出间隔不是单帧纯编码耗时，发送提交不是接收或屏幕完成时间。没有新增采集→显示全链路或跨机器时钟测量。

主控 `-latency-stats` 另增加 `present-interval`，统计实际提交新视频画面的间隔，帮助区分“平均 FPS 高但偶尔停顿”。最小化/还原和尺寸切换重置间隔基线，正常操作中真正的停顿仍计入；它不是面板扫描间隔，原有 RTT 也不是输入到画面的完整延迟。普通启动仍只增加一次发送开关状态日志，不逐次打印临时重试。

测试中的一次缓冲错误在新路线保持 UDP/同一编码代次，关闭优化时按旧策略降级 TCP；持续缓冲错误和权限错误仍降级。合成 1080p120 的新旧 UDP/TCP 管线保持约 120 次/秒应用提交，但健康无拥塞样本不证明实际拖动更快或尾延迟下降。长时综合压力测试中，旧 CPU 回读兼容路线仍出现 FPS 未过线；单独复测通过，且保存的 4.17 与新版关闭/开启优化的无界面接收对照接近，完整限制见 `VERIFICATION.md`，不宣称所有压力测试全通过。重点两机复测全屏大窗口拖动、快速滚动及文件传输期间操作；保留 4.17 ZIP，也可用上述开关按相同参数作对照。

## 被控端分辨率与显示布局变化（4.16）

被控端不再把程序启动时的屏幕矩形当成永久尺寸。每次连接前重新读取显示器设备和当前尺寸，断开期间改分辨率后也能直接重新连接，不必重启被控程序。活动会话以轻量 Win32 枚举每 250 ms 检查布局，两次一致后确认变化；没有变化时不创建 DXGI 工厂、不探测编码器、不重启视频，不改静止桌面 FPS。原合成测试源不跟随本机显示配置。

改分辨率、改变屏幕原点/布局时，按 Windows 设备名称保持当前显示器，不只按旧尺寸或旧序号匹配。重新确认可用的采集/编码配置，优先复用原本工作的编码器及驱动兼容运行时；探测码流尺寸必须匹配新屏幕，探测结束还会重新检查显示配置，避免连续改尺寸时提交过期配置。当前屏幕移除时尝试剩余可用屏幕；临时没有可用屏幕或探测失败时保留设置并重试。连接前无可用屏幕会明确报错，不拿旧尺寸继续配对。

确认变化后增加屏幕代次，更新采集、鼠标坐标映射、视频尺寸和静态补丁状态，用新的编码关键帧通知主控重建解码与 GPU/兼容显示缓存。旧尺寸压缩帧和清晰补丁不会混入新画面；新画面确认前释放旧按键并拒绝旧坐标输入。H.264 若提前产出不同尺寸的 SPS，会阻止它以旧描述发送。改分辨率会有短暂的视频链路重建，时间受驱动与编码器初始化影响，但不需要断开整个会话；F7、F8 和剪贴板连接保持独立。

质量、FPS、锐化参数不变；显式 `-bitrate` 保留，自动码率沿用原有按新分辨率计算的预算。F7/F8 路径记忆和 F8 本地保存目录不受影响。本机测试覆盖模拟显示配置的 JPEG/H.264、UDP/TCP、多次尺寸/原点变化与离线重连，并读取真实 Windows 设备枚举；不会自动更改你的系统分辨率。实际模式切换/多显卡热插拔仍需两机验证。日志仅在变化/重试时输出 `[lan][显示变化]`。

## GPU 纹理直连显示与本地延迟诊断（4.15）

默认 `-gpu-decode auto`：Windows 原生 MF 硬件解码可用、使用 D3D11 显示并与新被控协商成功时，从解码器取得 NV12 显卡纹理，在 GPU 上完成原有颜色转换，再交给显示端原有缩放/锐化和无损补丁图层。省去这条路线整幅画面的显卡→CPU 回读、CPU 颜色处理和 CPU→显卡上传；仍有 GPU 内部复制和跨设备同步，不是“完全无复制”。三个私有共享 RGB 表面限制显存交接数量，不把解码器自己的参考/输出表面长期交给 UI 持有。

画面变化时旧清晰补丁的撤销也在 GPU 上完成，不变区域继续保留；可靠的远端清除仍保留。GPU 交接未就绪时 UI 让出后重试最新画面，不等待全部显示队列。不改变采集、编码、质量、分辨率、码率或 120 FPS 上限，也不降低静止桌面的发送频率。最小化仍保留基础视频和解码，停止显示缩放/绘制和远端独立补丁采样；GPU 解码表面仍更新，以便还原显示最新画面。

日志首次出现 `MF GPU shared-texture output ready` 表示已使用新路线。驱动/纹理共享不兼容时，先退回原 MF CPU-NV12 路线，再沿用现有 FFmpeg/软件解码恢复策略；显示兼容回退使用 BGRA，并重新同步清晰补丁。软件解码、FFmpeg 后端、BGRA 输出和 `-renderer d2d` 不使用新纹理路线。第一次建议保留 FFmpeg 作为后备，不增添 DLL、CUDA 或其他运行时。

```powershell
# 默认新路线，继续保留熟悉的画质与窗口参数
.\lan_controller.exe -connect 192.168.1.20 -q 100 -w 1920 -H 1080 -r sharp

# 同机对照：关闭共享纹理，保留原生解码 + CPU-NV12 回读 + GPU 显示
.\lan_controller.exe -connect 192.168.1.20 -q 100 -r sharp -gpu-decode off

# 需要定位响应慢时才开启；每约 5 秒一条本地分段统计
.\lan_controller.exe -connect 192.168.1.20 -q 100 -r sharp -latency-stats
```

`-gpu-decode on` 用于新双端的诊断，跳过自动模式的远端能力检查，但不强迫软件解码器/Direct2D 使用共享纹理。`-latency-stats` 默认关闭，统计控制输入本地排队、接收帧排队、解码提交到输出、GPU 上传/复制提交、已解码画面到显示提交的 p50/p95/p99，4.18 增加新画面的提交间隔；每项最多保留最近 512 个样本，每次输出清零，不记录命令/输入内容。它不是采集→网络→物理显示的全链路延迟；GPU 数字是 CPU 提交耗时，不是 GPU 执行完成时间。控制通道 RTT 也不能替代操作到画面变化的延迟。

本机合成 1080p120 的 UDP/TCP 新路线测试达到约 120 次/秒解码与应用显示提交，1080p 放大至 2560×1440 的颜色/锐化像素对照通过；这不是两机实测提升百分比，也不保证软件编码被控机器能达到 120 个不同画面/秒。重点复测你的两机全屏拖动、滚动与首次操作响应；可用 `-gpu-decode off` 保持其他参数相同作对照。

## 持续送帧，仅最小化节能（4.14）

根据两机实测的大窗口拖动退步，4.14 移除更新驱动的 H.264 采集开关，`ddagrab` 固定恢复 `dup_frames=1`。桌面静止也保持原协商帧率的持续视频节奏，不做静止降帧、自适应 FPS 或最小化时的编码重启；质量、分辨率、码率、锐化参数不变。静止视频会继续占用采集/编解码资源，这是优先保证操作体验的明确取舍。JPEG 差分在没变化时本来就不编码画面，沿用其旧行为。

最小化时停止本地视频重绘消息与 GPU 提交，暂停被控端独立无损补丁的截图、比较和 PNG 编码。基础视频继续持续传输与解码，主控保留最新画面，因此还原不主动重连、请求关键帧或丢失参考链。还原立即唤醒补丁采样，不等待后台定时器；旧补丁继续按画面变化撤销，静止区域在正常约 400 ms 稳定期后重新校验/修复。失去焦点但没有最小化不触发这项节能。本版没有深度暂停，也不释放全部显存。

剪贴板、F7 命令行、F8 文件传输、鼠标状态同步、键鼠设置和会话连接不受最小化影响。正常显示恢复原 10 ms UDP 超时维护，不额外发送保活包。仅最小化且没有待拼接分片时使用 250 ms 接收超时；来包立即唤醒，缺片维护仍为 10 ms。后台的 56 字节加密 UDP 保活与视频分开，不触发解码/绘制，并以最后实际发送的帧号避免掩盖视频丢失。转为 TCP 后结束不再需要的 UDP 接收/保活轮询。

不需要再加 `-idle-video=false`。这个旧参数仍接受以兼容启动脚本，但无论 true/false 都不重新开启静止降帧。启动探测与正常视频使用同样的持续采集节奏。此前 4.13 的短时间 CPU 节省结果不代表拖动体验改善；验证详情和限制见 `VERIFICATION.md`。

绑定网卡不能绕过 VPN 的局域网隔离、Kill Switch、管理员防火墙策略或路由器客户端隔离；这些场景需在相应软件中允许局域网访问/分流。本版不添加中继，也不更改原云端版本。

主控窗口按 **F7** 打开命令与设置，关闭“同步键鼠”即看板模式；**F10** 恢复原版语义，取消当前文件操作，不再切换输入。切出窗口、断开连接或关闭同步键鼠时会释放远程按键和鼠标按钮。Alt+Tab、Win 键等通过低级键盘钩子在窗口前台时转发，Ctrl+Alt+Del 安全注意序列不在普通用户进程能力范围内。

默认 **Mode: Func**：F6 切换被控屏幕，F7/F8/F10 使用本地功能，F11 切换全屏。主控画面前台时长按 **F9 3 秒** 切换 **Mode: Key**，此时 F6/F7/F8/F10/F11 和 Esc 都是正常远端按键，本地功能栏隐藏；再长按 F9 3 秒恢复 Func。F9 短按松开后发送一次远端 F9，不会切换模式；看板关闭键鼠同步时也不发送该短按。

最大化按钮进入无标题栏、无边框的真全屏，覆盖当前显示器完整区域（包含任务栏位置）。Func 模式下把鼠标移到画面顶部约 4 像素内，会出现深色自定义标题栏，显示当前传输速率、FPS、Mode，并提供 F7/F8、退出全屏、最小化和关闭按钮；鼠标离开栏位自动收起。Func 模式下全屏时 Esc 也可返回原窗口。Key 模式需先长按 F9 恢复 Func，才可使用本地退出快捷键/顶部栏。F7/F8 为主控的附属窗口，打开时主动前置，不设置全系统永久置顶；在全屏状态也可以使用。

4.11 顶部栏的显示由鼠标是否真正位于主控/栏位上决定，不再因主控失焦被定时器反复隐藏；悬停不抢焦点，其他窗口遮挡主控时不从其后弹出。固定按钮、拖动期间不弹栏和 Key 模式隐藏仍保留。4.14 仅最小化采用轻量后台节能，基础视频和剪贴板同步生命周期仍独立。

**F6 切屏**在当前连接内循环可用显示器，标题栏显示屏幕序号与分辨率。被控重查显示器、先探测目标采集/编码器，再切换原点和尺寸；单屏/目标不可用时提示并保留当前画面。切换前释放按住的键鼠，等待新屏幕首张解码画面后恢复输入；旧压缩帧、无损区域、缩放/GPU 缓存不会混入新屏幕，文件与剪贴板连接不重建。DXGI 默认显卡上的输出沿用 ddagrab 索引；其他显卡/虚拟显示器以 GDI 桌面坐标采集，避免误抓同序号屏幕，这类屏幕的采集性能可能较低。启动 `-monitor` 的原语义不变。快速重复 F6 不堆积探测；20 秒没有新画面时允许再次 F6 重试。枚举顺序不保证等于 Windows 设置中的显示器编号。

F7 提供同步键鼠、同步剪贴板、远端画面鼠标、主控本地鼠标四个可选项。默认**不绘制远端画面鼠标**，主控本地鼠标显示。远端鼠标选项只改变视频采集是否叠加鼠标，不隐藏被控电脑自己的系统鼠标；切换可能重启编码器并短暂停顿。开启远端画面鼠标时暂停独立 GDI 无损修复，避免两条采集链的鼠标交替显示。设置在当前连接内保留，重新连接恢复默认。关闭剪贴板同步会取消主控当前同步，并阻止双方后续写入。

4.12 修复无鼠标设备被控端引发的指针消失：Windows 可以上报远端鼠标隐藏/受抑制，旧 LAN 主控会把这个状态照搬为本地隐藏，覆盖 F7 已勾选的设置。现在“显示主控本地鼠标”具有明确优先级，勾选时保留可见的本地指针并同步可识别的形态，未知形态兜底箭头；不必点击或拖动才显示。取消勾选仍会隐藏画面内的本地指针，顶部栏、黑边和弹窗保持正常鼠标。远端原始可见状态仍接收，但不再作为隐藏本地指针的依据；没有修改任何系统 ShowCursor 计数、被控设备或驱动。拖动捕获期间也刷新本地形态/设置，失焦悬停仅在鼠标真正位于主控上时更新，不改变其他窗口的鼠标。每个会话首次收到远端不可见状态时最多记录一条诊断，不重复打印标题栏或每次形态变化。远端视频里的鼠标仍由原有采集器叠加，4.12 不额外制造第二个画面鼠标，也不改变 draw_mouse 参数。

F7 的工作目录首次默认为被控 EXE 所在目录，4.17 将上次有效的执行路径仅记在被控进程内存中，关闭主控重新连接仍保留，被控程序重启后恢复程序目录；与 F8 浏览目录分别记忆。修改路径后无需执行命令，输入框失去焦点、关闭 F7 或正常关闭主控时会尝试更新远端记忆；正在执行的命令也更新有效路径。强制结束主控或断网前未送达的编辑不保证保留。命令中的 `cd` 不会回写这个输入框。命令回车或点击“执行”，上下键浏览本窗口的命令历史，输入框及输出支持 Ctrl+A。等待默认 10 秒，可选 0–3600 秒；0 只启动，等待超时或关闭窗口只停止等待，不终止远端进程，与原版语义一致。显示输出和退出码，输出最多 2 MiB，同时最多 4 个运行中的命令。命令以被控进程账户权限运行，仅向可信主控提供配对码；这不是权限隔离的命令沙箱。

4.11 修复 F7 输出滚动叠字：使用不透明文字背景、父窗口裁剪子控件，并在输出框完成滚轮/滚动条/键盘滚动后重绘该控件。没有改变字体大小、颜色、执行语义或视频绘制频率。

4.9 修正鼠标拖动链路：被控端不再只用 `SetCursorPos` 改变位置，而通过 `SendInput` 注入与按下/松开同一输入流中的绝对移动，支持负坐标的多显示器布局，拖动移动不合并 Windows 鼠标消息。主控按住拖动时不弹出顶部栏或重置远端按键；越出画面继续发送边缘坐标，所有按住的鼠标键都松开后才解除捕获。丢失焦点/捕获、打开 F7/F8、切换看板模式会安全释放输入，避免卡住按键。针对资源管理器路径文字拖选、系统音量滑块和 Win+Shift+S 选区的共同输入问题，保留原视频采集、画质及渲染参数。注入仍受 Windows 权限限制，不提供 UAC/安全桌面控制。

## 主控原生 H.264 解码（4.10）

4.10 引入 Windows Media Foundation H.264 解码，返回 CPU NV12 接现有 GPU 显示、锐化和静态清晰补丁；4.15 在符合条件时改用上面的共享 GPU 纹理路线，原 CPU NV12、BGRA / Direct2D 对照仍保留。移除原生路线的 FFmpeg 解码子进程、FLV 本地封装与进程间管道，网络仍使用原 Annex-B H.264，不改被控端采集/编码、质量/码率/FPS、UDP/TCP 或输入功能。Windows 提供的接口见 [原生 H.264 解码器](https://learn.microsoft.com/en-us/windows/win32/medfound/h-264-video-decoder)。

主控选择方式（保留其他连接、画质及尺寸参数）：

```powershell
# 默认：原生优先，不可用/解码失败/持续近期积压且有运行时时退回 FFmpeg
.\lan_controller.exe -connect 192.168.1.20 -q 100 -r sharp -decoder auto

# 只使用原生解码，便于确认没有静默切回 FFmpeg
.\lan_controller.exe -connect 192.168.1.20 -q 100 -r sharp -decoder mf

# 保留 4.9 的 FFmpeg 解码路线作同机对照
.\lan_controller.exe -connect 192.168.1.20 -q 100 -r sharp -decoder ffmpeg
```

`-software-decode` 在两种后端及回退后都保持 CPU-only。`auto` 中原生失败会优先退回已有 FFmpeg；只使用原生/没有 FFmpeg 时，原生 D3D11 故障或持续积压可以改用原生软件解码。`mf` 不跨到 FFmpeg；原生软件单纯达不到目标 FPS 不会因此断开连接，但真实解码错误/不支持的格式且无可用后端时会明确记录原因并结束会话。系统媒体组件缺失且主控没有 FFmpeg 时自动协商区域 JPEG；显式 `mf` 则明确报告组件不可用。已回退的后端不会因后续编码代次变化又被重选。

原生路线当前支持逐行、8-bit、4:2:0、偶数尺寸（48×48 至 4096×2304，具体硬件能力另受显卡/驱动限制）。依据 SPS 的颜色信息处理 BT.601/BT.709、有限/全范围并保持原 NV12 显示约定；不支持的矩阵/色度位置等会回退，不按分辨率猜颜色。复制时检查步长、平面和裁剪尺寸。日志只记录首帧（MF 计时包含激活）、故障和后端切换；D3D11 标记表示已配置解码设备，不承诺所有显卡都一定更快。

本机 1080p60 原生硬件及软件解码通过，主控不带 FFmpeg 的 UDP/TCP H.264 会话约 60 FPS。相同动态码流的独立解码 A/B 显示稳态耗时与 FFmpeg 接近，不能承诺 CPU 降低或全面降低操作延迟。120 FPS 压力测试曾暴露原生回读路线约 105 FPS、反复恢复的问题；现已增加跨恢复代次的近期本地排队判断，自动模式及时退回 FFmpeg，而不是加大日常缓冲、降低画质或放宽测试标准。纯原生高帧率能力仍取决于机器；首次测试建议保留 FFmpeg。具体数据及限制见 `VERIFICATION.md`。

## 120 FPS 与画质

两端默认目标和上限均为 120 FPS、原生屏幕分辨率；协商结果取双方 `-fps` 设置较低值，可在两端用 `-fps 60` 降回原目标。主控 120 Hz 不代表被控端桌面一定有 120 个不同画面/秒，真实更新还取决于被控刷新率、采集、编码、解码及显示性能。标题显示“实际显示/协商目标 FPS”；显示计数是应用实际绘制的新视频帧数，不代表面板扫描帧数。优先 Desktop Duplication + NVENC/AMF/QSV；硬件不可用时依次尝试软件 H.264 和 JPEG。日志明确记录实际选择，声明支持某编码器并不等于该硬件能正常工作，启动时会实际编码探测。

如果被控桌面实际只有 60Hz，通常每秒只有约 60 次新的桌面画面更新。4.14 恢复 `ddagrab` 的 `dup_frames=1`，维持视频节奏，标题达到 120 FPS 不等于远端每秒有 120 个不同画面。[FFmpeg 文档](https://ffmpeg.org/ffmpeg-filters.html#ddagrab)说明了该重复帧行为。标题 FPS 仍统计实际提交的视频帧，不是逐像素去重后的更新数。此前 `testsrc2` 合成源及 2K 测试视口的约 120 FPS，验证的是视频管线和应用提交能力，不能证明 60Hz 被控桌面的真实 120 FPS，亦不能证明物理 2K/120Hz 显示效果。编码/解码等待时间的对照仍有参考意义，但不是完整操作到显示的延迟。可用两端 `-fps 60` 做实际拖动/滚动对照；本次不自动降低上限、不改显示器设置。

3.1 提高默认画质：JPEG Q90 改为 Q100，NVENC CQ18 / 软件 x264 CRF18 改为 14。H.264 默认码率预算改为自动随分辨率和协商 FPS 缩放：1080p60 40000 kbps、1080p120 80000 kbps（最低 4000、最高 200000）；显式 `-bitrate` 则保持用户值。该预算不是对网络测速或承诺实际占满带宽。网络丢帧仍可降低码率，但主控解码排队丢帧不再被误判为网络拥堵。H.264 动态画面仍是有损编码，不能保证彩色小字与无损截图完全一致；静止无损修复保持开启。

显示窗口默认尽量按远端原生尺寸打开，超出本地主屏工作区才按比例缩小。`-w 1920 -H 1080` 指定初始内容尺寸，不改变被控采集分辨率。`-r sharp` 放大时采用原版路线的端点对齐双线性缩放，超过 1.08 倍后使用五点边缘锐化（强度 52、阈值 6）。4.6 默认使用 D3D11 GPU 两遍处理，保留相同算法和量化；不再每帧在 CPU 上生成整幅 2K 锐化图，也不把放大后的图再上传显卡。原生 1:1 保留原始像素，缩小采用平滑采样。`-r pixel` 和 `-r smooth` 保留各自采样方式。主控窗口和 F8 使用深色主题。

4.6 清晰补丁使用独立 GPU 纹理与 64×64 有效区域掩码：只上传新补丁/变动掩码，不每帧在 CPU 上复制并合成整屏。新视频仍按原有规则撤销变化区域的旧补丁，不变区域继续保留无损像素。帧交接只保留最新已解码画面，绘制期间持有独立引用，上传/锐化/绘制不占用接收画面的共用锁；不会任意丢弃 H.264 压缩参考帧。GPU 提交队列限制深度，队列忙时让出 UI 线程并重试最新画面；最小化不继续绘制。

默认不需要新 DLL、CUDA 或额外安装包，使用 Windows 的 D3D11 / D3DCompiler 系统组件。设备不支持或发生渲染错误时回退原 Direct2D/GDI 和 CPU 锐化，清晰补丁与画质仍保留。可用 `-renderer d2d` 强制原显示路线作同机对照；`-render-stats` 可选每约 5 秒打印上传/提交的 CPU 耗时、已解码画面的本地提交年龄及被新画面替代的显示帧数。这些数字不等于 GPU 实际执行时间、网络延迟或操作到屏幕亮起的完整延迟；显示替代帧不计作网络丢包。

4.7 默认让 H.264 解码器输出 NV12，而不是在 FFmpeg 中转换整屏 BGRA。主控端只上传亮度/色度两个平面，由 GPU 在源分辨率转换 RGB，再走 4.6 的原缩放/锐化与独立无损补丁图层。1080p 每帧的本地解码管道和基本视频上传量从 8,294,400 字节降至 3,110,400 字节（减少 62.5%）；这是本地内存/管道数据，不是网络带宽减少。采集、H.264 编码质量、码率、网络协议与 FPS 上限未改。硬件解码仍要下载到 CPU 内存，因此这一步不是全 GPU 零拷贝，也不减少 FFmpeg 文件大小。

原始 NV12 管道不带颜色元数据，FFmpeg 按输入标记显式统一为 BT.601 有限范围、左侧/垂直居中色度；GPU 正确恢复 RGB 全范围，亮度和色度变化都会撤销对应旧补丁。静止无损补丁仍是 RGB，不经过有损 YUV 转换。新旧 FFmpeg 均支持这条路线。颜色转换/色度采样与旧 FFmpeg BGRA 不承诺逐像素完全相同，但不会通过降低编码质量提高帧率；颜色、黑白范围和 GPU/CPU 算法有独立回归测试。

`-decode-output auto` 是默认值；`-decode-output nv12` 优先新路线；`-decode-output bgra` 保留 4.6 的解码输出＋GPU 显示，适合对照 NV12 优化。`-renderer d2d` 自动使用 BGRA 解码，避免长期在 Go 中转换整屏 NV12。GPU 初始化/运行故障先用 CPU 临时转换维持画面，再重启为 BGRA 解码；NV12 输出不可用时也有 BGRA 回退。硬件解码持续排队仍可切换 CPU 解码（CPU 同样可以输出 NV12），4.8 改为近期持续积压判断，不再累计三次排队丢帧就永久降级。启动期的延迟帧、一次性突发和很久以前的积压不会单独触发该降级；真正的解码失败/持续积压仍保留回退。这些重启可能短暂停顿，日志只记录首帧、故障及切换。

4.8 被控端让 FFmpeg 使用带长度的 FLV/AVC **本地管道封装**，一帧编码完成后即可取出，不再等下一帧的 AUD 来确认上一帧结束。编码 NAL 载荷不重新压缩，采集、CQ/CRF、码率预算、GOP、无 B 帧和鼠标参数保持原值；网络仍发送原来的 Annex-B H.264，UDP/TCP 协议不变。FLV 不在网络上传输。IDR 会保留/补齐 SPS/PPS，恢复时仍以完整关键帧重建参考链，不随意丢弃压缩参考帧。

恢复请求按编码代次合并：新编码器尚未发送首个关键帧、或旧编码器正在关闭时，不因重复关键帧请求再启动一轮；传输、鼠标和码率的设置变化有独立代次，不会被该合并吞掉。正常主动恢复去掉固定 150ms 等待；首次编码失败也立即重试，连续快速失败才以 50ms 起、最多 1s 的退避避免空转。FFmpeg 进程启动/显卡初始化仍需要时间，本版不承诺恢复完全无停顿。

4.8 接收队列增加到 32 帧，只给硬件解码启动期余量（16 帧在 120 FPS 下仅约 133ms，可能短于初始化时间）。正常流仍限制最多 4 帧排队；显示仍只保留最新已解码画面，不靠扩大日常缓冲提高 FPS。4.10 保留这些上限，增加原生 Media Foundation 解码后端；4.15 增加共享 GPU 纹理交接。FFmpeg 编码运行时瘦身尚未实现。

保留你原来的连接参数即可测试；要与 4.6 同机对照，另一次启动时加上 `-decode-output bgra`，不要同时更改质量、帧率或缩放参数。可追加 `-render-stats` 辅助比较本地提交耗时，但实际拖动/滚动响应仍以两机实测为准。

4.2 起显式 `-q 100` 对 NVENC / 软件 H.264 也生效：JPEG Q100，NVENC CQ8 / x264 CRF8，码率预算与 FPS 协商不变。未指定 `-q` 或 `-q 0` 保留原有 CQ14 / CRF14 默认，不自动加码率或改变服务器版本。其他显式质量值 20–100 映射到 CQ/CRF 28–8；AMF/QSV 仍沿用原来的码率模式。高质量会增加实际流量，H.264 仍是有损、色度采样仍与 JPEG Q100 不同，锐化不能恢复编码已丢失的细节。

独立鼠标状态同步约每 33 ms 采样、形态/可见性改变时经控制 TLS 通道发送，稳定状态每 2 秒补一次。主控画面内本地鼠标匹配远端的箭头、文本、手形、忙碌、十字、调整大小、禁止、帮助等系统状态；不移动主控实际鼠标位置。不论视频是否绘制远端鼠标都同步状态，F7 的本地鼠标隐藏选项仍优先。顶部栏、F7/F8、窗口边框和黑边保持本地控件的正常鼠标。支持复制的标准鼠标句柄识别；未识别的自定义/动画鼠标回退箭头，不传任意鼠标位图。

JPEG 回退现在是 `gdi/jpeg-delta`：首帧完整画面，之后以 64×64 块检测变化、合并相邻变化块，只编码和发送对应区域；接收端在已有画布上按序合成。不变区域不重新编码，不会因反复有损合成逐渐模糊。多个分离小变化不强行扩大成一个整屏包；变化面积超过 60%、区域超过 64 个时改为完整帧，持续变化时约每 3 秒补完整参考帧（质量始终一致，编码源始终是原始截图）。静止时每约 500 ms 发 16 字节视频载荷的保活更新，不重新编码整屏，也不重绘；标题里的 FPS 是实际更新次数，静止时低 FPS 正常。

区域更新沿用加密 UDP 分片及补发；乱序会等待前面的更新，漏帧/解码失败会请求完整帧重同步，而不是带着缺失区域继续绘制。大幅运动仍可能走整帧 JPEG，GDI 采集/软件 JPEG 的 CPU 开销仍在，因此不承诺区域 JPEG 全屏动画也能 60 FPS。主控既没有可用原生解码器、也没有 FFmpeg 时会协商区域 JPEG（被控端自动模式）；显式 `-decoder ffmpeg` 且不带运行时也保留该旧协商方式。

FFmpeg 子进程隐藏运行。H.264 使用短 GOP、无 B 帧、低延迟参数；主控默认优先原生 MF，FFmpeg 对照路线仍优先 D3D11VA，故障/持续积压保留后端或 CPU 回退。显示默认 D3D11，异常时回退 Direct2D/GDI。两条解码路线均先输出 CPU NV12，再按源分辨率上传显卡，兼容路线可输出 BGRA，仍非完全零拷贝；被控编解码配置、网络协议及 FFmpeg 文件未更换/裁剪。

动态画面通过 UDP；使用 1200 字节以内的 AES-GCM 加密分片，处理乱序、重复和少量缺片补发。分片等待上限 100 ms，超时或编码参考链损坏时等待 IDR，并请求编码器重启生成关键帧。严重丢帧时降低码率预算。当前关键帧请求通过重启编码进程实现，恢复时可能出现短暂停顿。

4.1 改为区域无损修复：每 100 ms 检查 64×64 区域变化，只撤掉发生变化的区域；稳定约 400 ms 的区域通过 TCP/TLS 补 PNG，不变区域保留无损像素，不再因别处输入/变化而整屏回落到 H.264。大修复分为最多 1024×1024 的 PNG 块，主控把修复层合成到原生尺寸画面，再统一缩放，不针对全屏降低编码分辨率或质量。高速运动区域仍使用有损 H.264，色度采样仍可能影响小字，不承诺与 JPEG Q100 或原版锐化完全一致。`-refine=false` 或开启远端视频鼠标会暂停该修复功能。

标题栏每秒更新实际显示 FPS、上下行速率、UDP/TCP、采集/编码后端、控制通道 RTT，以及文件传输/剪贴板重试状态；主控 `logs` 默认只记录重要事件，不重复打印完整标题。可选 `-render-stats` 才会记录显示性能统计。上下行以主控端为视角：↓ 收到的数据、↑ 发出的数据，包含视频、静态修复、控制、剪贴板和文件的 TCP/TLS 实际字节与 UDP 载荷（含加密/应用分片开销），不含 IP/以太网包头。RTT 是控制消息往返时间，不是画面到显示的延迟。静态修复、显示缩放、Wi-Fi 丢包、GPU 驱动、4K 屏幕都会影响结果；1080p 动态测试源的本机结果不能替代两台机器实测。

## 常用参数

```powershell
# 手动选择屏幕（0 起始，DXGI 输出与 Windows 枚举在特殊虚拟显卡上可能不同）
.\lan_client.exe -monitor 0

# 目标码率单位 kbps；默认 0 自动预算，硬件 VBR 上限为预算的两倍
.\lan_client.exe -bitrate 30000

# 两端默认 120；可以显式设置或降回 60
.\lan_client.exe -fps 120
.\lan_controller.exe -connect 192.168.1.20 -fps 120

# 熟悉的主控尺寸、锐化及高画质参数（4.2 的 -q 也影响 NVENC / x264）
.\lan_controller.exe -connect 192.168.1.20 -w 1920 -H 1080 -r sharp -q 100

# 默认 GPU 路线；仅作诊断时加日志，或强制旧显示路线作对照
.\lan_controller.exe -connect 192.168.1.20 -q 100 -r sharp -render-stats
.\lan_controller.exe -connect 192.168.1.20 -q 100 -r sharp -renderer d2d

# 定点诊断
.\lan_client.exe -capture gdi -encoder libx264
.\lan_client.exe -encoder h264_nvenc
.\lan_controller.exe -connect 192.168.1.20 -code <码> -software-decode
.\lan_controller.exe -connect 192.168.1.20 -code <码> -transport tcp

# 只发现设备
.\lan_controller.exe -list
```

不带 FFmpeg 时可以使用区域 JPEG/GDI 回退，也可在被控端用 `-encoder jpeg` 强制测试这条路线。可用 `-ffmpeg C:\path\ffmpeg.exe` 指定运行时。最新运行时与旧 NVIDIA 驱动可能不兼容；程序检测到 NVENC API 版本不匹配时，会尝试旁边的 `ffmpeg-compat.exe`。

每个被控端接受一个活动主控；可以运行多个主控程序连接不同机器。连接建立时使用配对码和 TLS 通道绑定双向认证，UDP 会话密钥来自 TLS，应用不会开放未配对的输入接口。音频、后台服务、UAC/锁屏控制未实现；并非原版所有功能都已移植。

## 剪贴板和 F8 文件传输

4.5 针对 H.264 操作响应：主控保留已收到视频帧的完整边界，在本地解码管道用 FLV/AVC 帧封装（只是换封装，不重编码，不改变网络 UDP/TCP 或画质），避免裸 H.264 输入解析器等待下一帧；输出 BGRA 固定单帧线程，取消原先 rawvideo 输出阶段的额外帧缓存。新增跨解码进程的输入/输出积压监测，启动宽限 500ms 后，如果硬解码连续 6 帧超过 max(40ms, 两帧周期)，或内部积压超过 4 帧且最旧帧超过 80ms，则自动切换软件解码，避免“高 FPS 但一直显示旧画面”。正常硬解码不强制切换；`-software-decode` 仍可手动选软件解码。具体机器上的采集、编码、网络、CPU 锐化和屏幕显示仍有延迟，这不是端到端零延迟保证。JPEG 回退路线、编码质量、码率和 FPS 上限均不变。

4.4 恢复 4.2 的默认 GUI 字体字号、字体和文字颜色，仅将字重改为 600。全屏顶部新增“固定 / 取消固定”，固定后鼠标离开仍保留栏位；取消固定恢复顶部悬停显示，Key 模式和退出全屏仍隐藏。主控将重复刷新通知合并，并立即绘制最新帧，避免持续的视频通知挤压低优先级 WM_PAINT。高清静态补丁在对应区域的已解码视频明显变化时及时失效，不再完全依赖被控端 100ms 的检测/可靠清除通知；未变化区域保留修复。忽略小幅编码噪声，极细小/低对比度变化仍由原有可靠清除处理。编码质量、FPS 和服务器版不变。

文字和图片双向自动同步，不需要按 F8。图片支持常见 Windows PNG、24/32 位 DIB/DIBV5 截图，单张 PNG 上限 24 MiB、1600 万像素；文本 UTF16（含结束符）及 UTF8 网络内容各上限 2 MiB，超限留在本机不截断。复制文件产生的 CF_HDROP 不同步，不实现跨端粘贴文件。图片写入同时提供 PNG 和 DIB，方便常用应用粘贴。特殊调色板/压缩 DIB、只有 CF_BITMAP 的旧式应用格式暂不支持。

剪贴板使用独立、经过会话认证的 TCP/TLS 连接及 128 KiB 分块、SHA256 校验，不往控制通道塞大截图。轮询约 600 ms，忙碌/读取失败会继续重试；检查复制版本及目标剪贴板序号，避免传完大图后覆盖刚复制的新内容，并用内容摘要抑制同步回环。两端同时复制不同内容时，当前轮询中主控端新内容优先；这不是多主编辑的冲突合并。连接刚建立时两端内容不同也按该规则处理。

主控画面按 **F8** 打开文件管理，再按 F8 关闭（会取消仍在进行的操作）。远端目录首次默认为被控 EXE 所在目录，4.17 每次成功浏览后只更新被控进程内存，关闭主控重新连接恢复上次目录，被控程序重启后恢复程序目录；“磁盘”总览也只在该进程存活期间记住。无效路径不覆盖之前记录，已记住目录临时不可用时退回程序目录。默认本地“保存到”目录和其原有会话记忆逻辑未改，仍是主控 EXE 所在目录。“磁盘”按钮可进入磁盘选择。路径输入回车/刷新进入目录，双击目录进入，`..` 返回上级；搜索当前目录，路径和搜索输入框支持 Ctrl+A。

两项远端路径使用同一个被控进程内的加锁内存对象，F7/F8 互不覆盖，多个主控先后连接该进程共享其最近路径。4.17 不再读取或生成 `mydesk-lan-paths.json`，也不读写 AppData 路径设置；旧版本留下的配置文件会被忽略，不自动删除。只对目录是否有效作正常文件系统检查，不将路径记忆写入磁盘。协商能力仍是 `directory-memory-v1`，无需改变主控使用方式。

4.11 F8 使用原生虚拟 ListView，真正分为**文件名 / 大小 / 修改时间**三列：文件名随窗口伸展，大小右对齐并按实际数值排序，长文件名可悬停查看，目录仍只加末尾 `\`。点击表头切换排序，目录在文件之前、`..` 固定最上方；排序/过滤按真实路径保留选中项。文本从本地列表缓存按需绘制，滚动不请求网络，v6 公共控件双缓冲减少闪烁。深色表头与进度条不改变原有字号；公共控件激活清单在系统临时目录自动创建/释放，无须复制额外依赖文件。

双击远端普通文件直接下载到“保存到”目录，无需每次弹出保存对话框；同名文件自动加 `(1)`、`(2)` 后缀，不覆盖旧文件。“保存到…”选择本地目录，当前会话关闭/重开 F8 会记住该目录。把本地普通文件拖入 F8 窗口即可上传到当前远端目录，也保留多选上传、下载按钮；上传覆盖远端已有文件仍需确认。F8 显示可视进度条、百分比、已传/总量、速率；数据传完后仍需校验/保存，最终显示校验成功才算完成。标题栏另显示进度。LAN 是端到端传输，没有原版中转服务器的第二段进度，因此只显示一条真实进度条。F10、取消传输或关闭窗口会中止正在执行的文件操作；“命令 F7”按钮打开命令设置。目录递归传输仍不支持。

上传/下载另开经过会话认证的 TCP/TLS 连接，与视频和键鼠通道分离。文件先写同目录临时文件，经完整 SHA256 校验后才发布目标文件；失败/取消清理临时文件。覆盖已有文件必须明确确认，失败不覆盖原文件；源文件在传输期间发生可检测的大小/修改时间变化会报错。暂不支持目录递归传输、删除、断点续传或文件剪贴板。传输功能允许配对主控访问被控进程账户可读写的普通文件，请只向可信设备提供配对码。

## 构建与验证

```powershell
.\install-runtime.ps1
.\install-compat-runtime.ps1  # 可选：较旧的 NVIDIA 驱动
.\build.ps1
```

单独 Go 模块，无第三方 Go 依赖。Go 1.24+，指定工具链 Go 1.25.7。只构建 Windows x64；两个程序需要分别构建 `./cmd/client`、`./cmd/controller`。

常规测试覆盖区域 JPEG 编解码/合成、静止保活、丢失参考帧重同步、无 FFmpeg 的 UDP/TCP 会话、网卡选择、多地址连接、防火墙脚本范围与转义、认证拒绝、发现、UDP 分片/补发/重复/超时、H.264 参考依赖与自动 TCP 降级。防火墙测试不实际修改本机规则。原生 COM/GDI 指针触发 vet 的 `unsafeptr` 静态提示，其他检查可用 `go vet -unsafeptr=false ./internal/lan`。

```powershell
$env:MYDESK_LAN_MEDIA_TEST='1'
$env:MYDESK_LAN_UI_TEST='1'
go test -v -timeout 100s ./internal/lan
```

以上启用动态测试源的真实编解码、加密 UDP/TCP、原生解码颜色/恢复及无需主控运行时的 H.264 会话，并打开自动关闭的原生显示测试窗口；不注入真实键鼠、不同步测试机剪贴板。全量 GPU/桌面测试可再设 `MYDESK_LAN_GPU_TEST=1`、`MYDESK_LAN_DESKTOP_TEST=1` 并使用 `-timeout 240s`。独立原生/FFmpeg 解码延迟对照需设 `MYDESK_LAN_MF_LATENCY_TEST=1` 并只运行 `TestNativeMFDecoderLatencyAB`，数字不包含桌面采集/网络/显示。也可以用两端程序的 `-source test` 和 `-test-seconds 10` 做无输入接收测试。

运行时来自 [FFmpeg 官方下载页面推荐的 Gyan 构建](https://ffmpeg.org/download.html#build-windows)。现代运行时为 FFmpeg 9.0.2，安装时校验发布方 SHA256。FFmpeg GPLv3 许可证附在发行目录；运行时作为独立进程使用。兼容运行时的来源及对应源码见 `THIRD_PARTY.md`。
