## LAN 4.20 / key-only discovery and explicit same-key target selection

- Scope is only LAN connection setup. The master first accepts the existing pairing key, discovers candidates and runs a lightweight authenticated TLS probe. One free matching device connects automatically; multiple matching devices always require a selection, even if only one is free. Occupied devices stay visible but cannot be selected by index; no takeover. No matches / all busy can rescan, change key, enter an IP or quit. Blank selection rescans, invalid input retries, EOF/cancel does not pick a default device. Explicit -connect bypasses discovery/matching and never falls back to another host. -list requires no key and starts no session.
- Additive discovery capability key-match-v1 and match-probe/match-result messages retain protocol v6. Discovery contains a random process identity, name, addresses and capability, not the key, key hash or HMAC proof. Probes use the existing TLS exporter with distinct match-controller/match-client HMAC roles and check both sides. Session objects, capture/encoder/decoder selection, UDP video sockets, input release and clipboard work are not created by probing. A busy probe reads only the session pointer under the existing mutex. Formal pairing rechecks occupancy rather than treating the probe as a reservation.
- Addresses are checked individually (duplicate address suppressed), with up to four workers, 128 addresses per pass, a six-second pass budget and two-second per-address budget. A stale first address cannot suppress a reachable alternate. Results are merged only by authenticated process identity, in discovery address-priority order; forged/identical advertised IDs and identical hostnames do not merge distinct hosts. Known legacy candidates are not probed using full pairing. Match names are one-line/control-character sanitized. Matching output does not print supplied keys; the host's pre-existing pairing-code display is unchanged. No key file or server dependency is added.
- New TLS/loopback tests cover right/wrong keys, occupied-session pointer/context preservation, no capture callback/session reservation, duplicate-key hosts, identical advertised IDs/hostnames, multiple addresses/stale-first fallback, bounded workers/address count, legacy skips, cancellation before/during probing, wrong-role and cross-connection replay rejection, forged reply rejection, and actual UDP metadata with a stable authenticated identity and no key/proof. Windows x64 on the workspace machine, NVIDIA T400 4GB / installed driver 552.22. Desktop output tested: 1920×1080. Actual end-to-end test uses a continuously changing 1920×1080 60 FPS synthetic video source, H.264 NVENC, authenticated TLS pairing, AES-GCM fragmented UDP or forced TCP, FFmpeg decoding and a native Direct2D window. Four seconds warm-up, then a three-second measurement:

| Transport | Sustained decode | Sustained display | Loss in stable final two-second interval |
|---|---:|---:|---:|
| UDP | 60.0 FPS | 60.0 FPS | 0 |
| TCP fallback | 60.0 FPS | 60.0 FPS | 0 |

One transient UDP frame loss occurred during startup of the final full-suite run; reference recovery succeeded. First hardware decoded frame arrived in approximately 170–200 ms from decoder launch. These are loopback tests on one machine, not two-machine LAN/Wi-Fi measurements or a motion-to-photon latency measurement.

The actual Desktop Duplication capture + NVENC probe separately produced 103 H.264 access units in 2.04 seconds, approximately 50.6 FPS including process/device startup. This short test verifies the real capture backend works; it does not establish sustained 60 FPS for all desktop workloads.
